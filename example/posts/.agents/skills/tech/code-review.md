# 代码评审清单（tech）

> 按「设计 → 功能 → 复杂度 → 测试 → 命名 → 注释 → 风格」的顺序逐项过改动。

## 用途

- 评审一次提交 / 一个 PR / 一段 diff。
- 在提交前自检，减少评审往返。
- 统一团队评审口径，把「感觉不太好」变成可讨论的点。

## 何时使用

- 提交前自检；
- 收到他人请求做评审时；
- 批量审查一批改动时。

## 输入

| 输入 | 说明 | 缺失时 |
|---|---|---|
| 改动内容 | diff 或文件列表 | 必须有 |
| 改动意图 | 作者想解决什么问题 | 缺失时先问，不要猜 |
| 关联上下文 | 相关模块、调用方、需求 | 缺失时读代码推断 |
| 仓库状态（可选） | 项目根有 `.git/` 时的 `git status`、diff 与基线提交 | 无 `.git/` 或 git 不可用时跳过，并在输出中说明 |
| 记忆（可选） | 源目录下的 `.agents/memories/` 中的项目目标、偏好、文风、结构与连续性约定 | 目录或文件不存在时跳过，不视为错误 |

## 执行步骤

1. **有 `.git/` 时先读仓库**：按「当前修改综合评价」一节收集状态、diff 与记忆，形成本次评审的基线。
2. **先读意图**：一句话复述这次改动要做什么；与 diff 不一致时先提出。
3. **按顺序过清单**：设计 → 功能 → 复杂度 → 测试 → 命名 → 注释 → 风格。
4. **分级评论**：
   - `阻塞`：必须改，否则不能合入；
   - `建议`：应该改，作者可自行决定；
   - `Nit`：纯打磨，作者可以忽略。
5. **给正面反馈**：明确指出哪些设计得好（便于作者保留）。
6. **给结论**：`通过` / `修改后通过` / `需要重做`，并说明理由。

## 当前修改综合评价（有 `.git/` 时）

> 项目根存在 `.git/` 时，评审对象不限于用户贴出的片段：把「当前未提交改动 + 最近基线 + 记忆」合起来看。

### 数据源

| 来源 | 读取内容 | 用途 |
|---|---|---|
| `.git/` | `git status --short`、`git diff --stat`、`git diff`、`git diff --cached`、`git log -1 --oneline` | 确认改动范围、暂存状态与基线 |
| 源目录下的 `.agents/memories/` | `project.md`、`preferences.md`、`style.md`、`outline.md`、`continuity.md` 等 | 对照项目目标、偏好、结构与连续性约定 |

### 规则

1. **只读**：不执行 `git add` / `commit` / `reset` / `checkout` / `clean` 等写操作。
2. **不遗漏未暂存改动**：`git diff` 与 `git diff --cached` 都要看；两者都为空时说明工作区干净。
3. **不编造**：git 不可用、输出为空或仓库无提交时如实说明，不虚构 diff、文件名或提交记录。
4. **以记忆为参照，不以记忆为事实**：记忆与代码冲突时以代码为准，并在评价中指出记忆需要修正。
5. **分开评价**：把「改动本身的质量」与「改动是否符合项目记忆 / 当前目标」分开写，避免混为一谈。

### 输入与输出

- 输入：git 状态与 diff、当前任务说明、源目录下的 `.agents/memories/` 中的相关条目。
- 输出：改动概览、与记忆的一致性、风险项、验证情况、明确结论。

## 评审清单

### 设计
- 这次改动是否放对了层？是否应该复用既有能力？
- 与周边代码的交互是否说得通？现在加这个功能是不是好时机？
- 接口是否暴露了本不该暴露的细节？

### 功能
- 是否实现了作者宣称的意图？意图本身对用户有价值吗？
- 边界条件：空值、空集合、极值、越界、并发、超时。
- 错误路径是否都被处理？错误信息是否可定位？
- 是否有静默失败（吞异常、忽略返回值、默认吞掉失败）？

### 复杂度
- 是否存在可以删掉的分支、抽象、配置项？
- 函数是否过长、嵌套是否过深、圈复杂度是否失控？
- 是否为「将来可能会需要」提前抽象？（YAGNI）

### 测试
- 是否与生产代码同一次提交？
- 测试是否真能失败（代码坏了会不会红）？
- 是否覆盖了这次改动的边界与错误路径？
- 断言是否精确（不是只断言「不崩」）？
- 测试之间是否互相独立？

### 命名
- 名字是否表达了意图而非实现？长度是否合适？
- 同一概念在不同文件里是否同名？
- 缩写、缩写缩写缩写是否需要展开？

### 注释
- 注释解释「为什么」，而不是「做了什么」？
- 有没有过期注释、与代码矛盾？
- TODO 是否带责任人与上下文？

### 风格
- 是否遵循仓库既有的格式化与命名约定？
- 是否夹带了与本次改动无关的重构 / 格式化噪音？

### 文档
- 改动是否改变了对外接口？接口文档是否同步更新？
- 是否有需要使用者知晓的行为变化（默认值、退出码、兼容性）？

## 评论分级示例

```text
[阻塞] src/net.cpp:88 —— 超时后仍然复用上一次的成功结果，调用方会拿到过期数据。
       建议：超时分支返回错误，或显式标记结果不可用。

[建议] src/cache.cpp:42 —— 这里用 map 保存 LRU，但项目里已有 LRU 容器实现，建议复用。

[Nit] 变量名 `tmp2` 建议改成 `parsedConfig`，读代码时不用回溯。
```

## 质量检查清单

- [ ] 先复述了改动意图再开始评审；
- [ ] 项目有 `.git/` 时读取了 status、未暂存与已暂存 diff，并说明基线；
- [ ] 项目有 `.git/` 时结合源目录下的 `.agents/memories/` 评价了改动与项目目标 / 偏好的一致性；
- [ ] 按固定顺序覆盖了全部维度；
- [ ] 每条评论有级别、位置、问题、建议；
- [ ] 阻塞项确实阻塞（风格偏好不应升级为阻塞）；
- [ ] 指出了做得好的地方；
- [ ] 结论明确；
- [ ] 没有把没读懂的地方写成「建议重构」。

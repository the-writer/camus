# 技术文章写作（tech）

> 把一次实现、一次排障或一次设计写成「别人能复现」的技术文章。

## 用途

- 把工程过程沉淀成教程、解析或复盘文章。
- 让文章既准确又可复现，不写成「配置截图流水账」。
- 控制技术细节密度，避免劝退读者。

## 何时使用

- 做完一个值得记录的功能或问题；
- 需要写使用文档 / 教程 / 架构说明时；
- 团队需要沉淀排障手册时。

## 输入

| 输入 | 说明 | 缺失时 |
|---|---|---|
| 实现或过程素材 | 代码、命令、报错、配置、时序 | 必须有 |
| 读者 | 会什么、想解决什么 | 向用户确认 |
| 环境 | 版本、依赖、平台 | 记录清楚 |
| 结论 | 这次做成了什么、代价是什么 | 从素材推断并与用户确认 |

## 执行步骤

1. **定读者问题**：文章回答读者遇到的**哪一个**问题（只回答一个）。
2. **定前置条件**：读者需要先知道什么（版本、概念、权限）。
3. **选体裁**：
   - **教程**（教做成一件事）：目标明确、步骤可跟；
   - **解析**（讲清原理）：概念 → 机制 → 例子；
   - **复盘**（讲发生了什么）：背景 → 时间线 → 根因 → 改进；
   - **决策记录**（讲为什么这么选）：选项 → 权衡 → 结论。
4. **搭骨架**：先写大纲，确认后再补细节。
5. **写最小可复现示例**：命令能直接复制粘贴执行；路径用占位但格式真实。
6. **写验证方法**：读者如何确认「成功了」。
7. **写失败与排错**：常见的坑与报错对照表。
8. **补环境信息**：版本矩阵表。
9. **自查**：跑「技术文章自检表」。

## 教程骨架

```markdown
# 用 <X> 实现 <Y>

<一句话说明读者能得到什么>

## 前置条件
- <环境 / 版本 / 权限>

## 步骤
### 1. <动作>
<命令或代码 + 为什么这么写>

## 验证
<如何确认成功，给出预期输出>

## 常见问题
| 现象 | 原因 | 处理 |
|------|------|------|

## 环境矩阵
| 组件 | 版本 |
|------|------|
```

## 技术文章自检表

| 检查 | 通过标准 |
|------|---------|
| 问题单一 | 全文只回答一个读者问题 |
| 可复现 | 命令 / 代码可直接执行，环境信息齐全 |
| 有解释 | 不只给步骤，还说清「为什么这样做」 |
| 有验证 | 读者能判断自己是否成功 |
| 有排错 | 覆盖最常见的 2–3 个坑 |
| 版本明确 | 版本 / 平台 / 依赖已列出 |
| 无内部黑话 | 内部代号、缩写已展开或替换 |
| 不含秘密 | 无密钥、内网地址、客户数据、真实个人信息 |

## 写作风格要点

- 代码块标注语言；命令块加 `$` 前缀或明确区分输入输出；
- 关键行加注释解释**为什么**，不复述代码；
- 错误信息原样贴出（脱敏），不要改写；
- 输出结果截取关键行，不要贴整屏日志；
- 解释用类比，但类比之后必须给准确表述；
- 避免「很简单」「只需」这类对读者不友好的措辞。

## 输出格式

```markdown
## 读者问题
<...>

## 体裁
<教程 / 解析 / 复盘 / 决策记录> —— 选择理由：<...>

## 前置条件
- <...>

## 大纲
1. <...>
2. <...>

## 正文骨架
### <小节>
- 讲什么：
- 证据 / 素材：
- 读者动作：

## 复现命令
```bash
# 输入
<命令>
# 预期输出
<关键行>
```

## 常见问题表
| 现象 | 原因 | 处理 |
|------|------|------|

## 环境矩阵
| 组件 | 版本 |
|------|------|
```

## 质量检查清单

- [ ] 文章只回答一个读者问题；
- [ ] 前置条件完整（版本、权限、依赖）；
- [ ] 所有命令 / 代码来自真实执行，输出为实际输出；
- [ ] 有验证步骤与预期结果；
- [ ] 有常见问题与排错；
- [ ] 涉及版本差异的地方已标注；
- [ ] 已脱敏（密钥、内网地址、客户名、个人信息）；
- [ ] 语言对读者友好，没有「显而易见」「只需」。

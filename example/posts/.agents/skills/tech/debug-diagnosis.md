# 故障定位与复盘（tech）

> 用「先止血、再定位、后复盘」的顺序处理线上问题，留下可执行的改进项。

## 用途

- 面对报错、崩溃、卡顿、结果不对时定位根因。
- 写出一份别人也能照着做的复盘。
- 把一次故障转化为下次的检查项或自动化用例。

## 何时使用

- 线上告警、用户报错、测试失败；
- 性能退化需要定位；
- 故障结束后做复盘。

## 输入

| 输入 | 说明 | 缺失时 |
|---|---|---|
| 现象 | 错误信息、日志、截图、复现步骤 | 必须有 |
| 影响范围 | 谁受影响、多久、有多严重 | 向用户确认或从告警推断 |
| 变更历史 | 最近的发布、配置、数据变更 | 从代码与部署记录查 |
| 环境 | 版本、配置、依赖 | 记录快照 |

## 执行步骤

### 阶段一：止血
1. **确认现象**：稳定复现或明确「偶发」；记录原始报错与时间点。
2. **评估影响**：是否影响全部用户？是否有数据损坏风险？
3. **止损**：回滚 / 降级 / 关闭开关 / 限流。**先止血再定位。**
4. **记录决策**：做了什么止损动作、为什么。

### 阶段二：定位
5. **缩小范围**：时间维度（何时开始）、版本维度（哪个发布）、数据维度（哪些输入）、规模维度（多大比例）。
6. **列假设**：按可能性排序，每个假设配一个验证方法。
7. **逐一验证**：优先验证「能解释全部现象」的假设。
8. **定位根因**：区分「触发原因」与「根本原因」（为什么这个缺陷能存在）。
9. **验证**：修复后确认现象消失，且相邻路径未回归。

### 阶段三：复盘
10. **写时间线**：从首次异常到恢复，按时间顺序列事件与决策。
11. **做无责分析**：问「系统当时能做什么才不至于这样」，而不是「谁没注意」。
12. **列改进项**：每条含「做什么 / 谁 / 何时 / 怎么验证有效」。
13. **沉淀**：把关键路径补成自动化测试或监控项。

## 定位手段

| 手段 | 适用 | 注意 |
|------|------|------|
| 二分定位（版本 / 数据 / 输入） | 变更引入的问题 | 需可回滚或可复现环境 |
| 日志时间线对齐 | 分布式、并发问题 | 注意时钟漂移 |
| 最小复现 | 逻辑缺陷 | 去掉无关因素直到必现 |
| 指标与追踪 | 性能退化 | 先确认指标口径没变 |
| 差分对比 | 「昨天好今天坏」 | 排除依赖与外部服务变化 |
| 断言与断点 | 逻辑错误 | 仅在可调试环境进行 |

## 复盘模板要点

```markdown
## 摘要
<影响范围、时长、根因一句话、恢复方式>

## 时间线
| 时间 | 事件 | 决策人 | 动作 |
|------|------|-------|------|

## 根因分析
- 触发原因：<...>
- 根本原因：<...>（为什么这个缺陷能存在）
- 放大因素：<为什么影响这么大>

## 处置有效性
- 有效：<...>
- 无效：<...>

## 改进项
| # | 改进项 | 类型 | 负责人 | 期限 | 验证方式 |
|---|-------|------|-------|------|---------|
| 1 | <...> | 预防 / 探测 / 缓解 | <...> | <...> | <...> |

## 沉淀
- 新增测试：<...>
- 新增监控：<...>
- 文档更新：<...>
```

## 质量检查清单

- [ ] 先记录现象与影响，再动手改；
- [ ] 止血动作与根因修复分开描述；
- [ ] 根因区分了「触发」与「根本」；
- [ ] 每个假设都有验证方法与结论；
- [ ] 复盘无责，聚焦系统与流程；
- [ ] 改进项有负责人、期限与验证方式；
- [ ] 至少沉淀了一条自动化测试或监控项；
- [ ] 未编造日志、指标或时间点（缺数据就标注缺失）。
